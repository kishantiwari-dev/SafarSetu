## Overview and verified stack

SafarSetu is a Flutter passenger app prototype for bus occupancy/seat availability estimates. It uses Dart and Flutter Material 3, with direct runtime dependencies `flutter`, `http`, `flutter_map`, `latlong2`, `shared_preferences`, and `url_launcher`; Flutter test/lint and the preferences platform interface are development dependencies. The SDK constraint is Dart `>=3.3.0 <4.0.0`; `flutter_lints` is pinned by the manifest to `^4.0.0`.

## Startup, screens, and navigation

`main()` → `SafarSetuApp` → `MaterialApp(home: LoginScreen)` → after local form checks and a simulated delay, push `HomeScreen`. Home is a stateful shell with four `NavigationBar` tabs: Home, Search, Trips, Profile. Home and Search expose the same stop form; swapping, required-field validation, a progress indicator, and recent-journey selection are local interactions. Search uses `BusRepository` (mock by default, API when configured), then pushes `BusResultsScreen`. Tapping a bus card pushes `BusDetailsScreen`. Empty result “Search Again” pops back. There is no named route table or deep-link handling.

## Backend, configuration, and persistence

The backend is a separate Maven module in `backend/` and the Flutter app can call it in opt-in API mode. The Maven manifest specifies Spring Boot 4.1.1, Java 21, Spring MVC, Spring Data JPA/Hibernate, Jakarta Validation, PostgreSQL JDBC, and Spring Boot test dependencies. The package is `in.safarsetu.backend`; `SafarSetuBackendApplication` is the entry point. No Flyway or Liquibase dependency/history exists. Tables/entities are `buses`, `routes`, `stops`, route-specific ordered `route_stops`, `tickets`, `bus_locations`, and `occupancy_snapshots`. Stable string IDs, foreign keys, unique fleet/ticket/idempotency identifiers, route order constraints, capacity/coordinate checks, and latest-record indexes are included. Base and production profiles use Hibernate `validate`; only the dev profile defaults to non-dropping `update`. This remains unsuitable as a reviewed production migration strategy.

`DB_URL`, `DB_USERNAME`, and `DB_PASSWORD` are required; no H2 fallback exists. No populated secrets are checked in. The default dev profile uses local CORS patterns, Hibernate `update`, and insert-only seed data. Explicit `prod` disables seeds, forces Hibernate `validate`, and configures PostgreSQL TLS hostname/certificate verification (`sslmode=verify-full`); exact CORS origins are opt-in via `CORS_ALLOWED_ORIGINS`. Hikari connection/validation timeouts and pool size are configurable. The dev seed has 8 simulated routes, 22 approximate stops, 8 synthetic buses, 18 simulated tickets, 19 simulated location records, and 8 snapshots. Normal track timestamps use fixed offsets from the seeder's UTC startup-minute anchor; stable existing rows are unchanged after restart. One bus has a deliberately stale point and one lacks location data. NMRC verifies some Aqua Line station names/order only; it does not verify simulated bus routes or coordinates.

Occupancy uses `OccupancyCalculator` with the inclusive boarding/exclusive destination rule: a ticket contributes when `boardOrder <= queryOrder && destinationOrder > queryOrder`. `RouteStopSequence` validates contiguous zero-based order and unique route stops. `BusService` validates IDs/relationships and returns route-stop occupancy in `OccupancyDto`; `TicketService` retains duplicate ticket/idempotency checks, route order, positive count, timestamp sanity, and configured passenger-capacity checks. Repository ticket order and `boardedAt` time do not filter or change the stop calculation. Duplicate ticket IDs, bad route/ticket relations, invalid sequence values, and total-capacity overflow return conflicts. Missing ticket data returns an unknown onboard value and `NO_TICKET_DATA`; no location returns `NO_LOCATION`, and stored `OccupancySnapshot` rows are not authoritative or used by the calculation. Provisional available seats are `seatingCapacity - onboardPassengers` under a one-passenger-per-seat assumption; negative values remain negative with a warning. No seated count is produced. `Ticket` now has nullable trip identity, which scopes occupancy and ingestion capacity checks. When records cannot be assigned to one trip, occupancy is unknown instead of combining journeys. Latest GPS is used only to choose the nearest route stop when no stop is supplied, with stale/future-location warnings.

REST endpoints and JSON contracts are documented in `backend/API_CONTRACT.md`: paginated bus/route/stop lists; bus details, route stops, route journey search, occupancy by current location or stop, latest location, and simulated ETM ticket ingestion. The Phase 5 Dart adapter maps bus/stop/occupancy/location DTOs; legacy `Bus.fromJson`/`toJson` remains for the mock model.

## Phase 4 REST API implementation record

The source API is handled by `HealthController`, `RouteController`, `BusController`, `BusService`, and `TicketService`. Reads map JPA entities to `BusDto`, `RouteDto`, `StopDto`, `LocationDto`, and `OccupancyDto`; ticket ingestion validates `TicketRequest` and returns a receipt with HTTP 201. `ApiExceptionHandler` standardizes validation, API exceptions, data-integrity conflicts, malformed input, and unexpected errors as `ApiError`, without stack traces or SQL details. Application data flow is controller → service → Spring Data repository → JPA entity/PostgreSQL, then service maps to DTO; occupancy uses the existing route-order calculator. The new route detail method returns `RouteDto` metadata; ordered stops remain a separate route endpoint. Location returns only the latest recorded location, source, and freshness (15-minute stale threshold); absent bus/location yields 404, invalid/inconsistent rows yield 409. Simulated seed locations remain `SIMULATED`, not live GPS.

The Phase 4 `HealthControllerTest` verifies the application health MVC endpoint; `RestApiControllerTest` source checks route detail/ordered-stop JSON, structured unknown-route errors, and ticket 201 behavior. `BusServiceTest` source covers route detail/invalid ordering and location freshness/absence alongside existing search/occupancy cases; existing ticket tests cover duplicate ID/idempotency and route/capacity validation. Because the test JVM restriction blocks Mockito inline-agent attachment, the mock-heavy service/API tests did not execute. No PostgreSQL behavior or database-backed live HTTP endpoint was verified. Flutter `Bus` JSON expects `route`, occupancy, ETA, and location text, while backend DTOs expose separate normalized values; integration needs a Dart adapter and must not present unknown/provisional values as authoritative. Phase 5 Flutter integration is **not ready to claim end-to-end readiness** until the full suite and PostgreSQL-backed app behavior are verified.

## Data freshness, comparison, and crowding slice (2026-10-25)

Backend occupancy responses now include `dataUpdatedAt` (latest selected-trip ticket event), `freshnessStatus`, and `crowdingCategory`; calculation time remains separate. Configurable default staleness cutoffs are 15 minutes for locations (`LOCATION_STALE_AFTER`) and 30 minutes for occupancy (`OCCUPANCY_STALE_AFTER`). Simulated records always report `SIMULATED`; separate location `stale` boolean retains age information. Real future timestamps report `UNKNOWN`, and missing occupancy reports `MISSING` / unknown crowding. Crowd thresholds default to <40% LOW, 40–69% MODERATE, 70–89% HIGH, >=90% NEARLY_FULL, based on total passenger capacity, with `CROWDING_MODERATE_PERCENT`, `CROWDING_HIGH_PERCENT`, and `CROWDING_NEARLY_FULL_PERCENT` configuration. Flutter API search now fetches service-calculated occupancy per result at the selected boarding stop and displays source, freshness, trip context, passenger count, and valid provisional seats. If the service says trip context is required, occupancy remains unknown. A detail warning suggests only same-journey alternatives with known, fresh, real-source lower-crowding estimates; simulated, stale, missing, and unknown data do not qualify. API failures do not switch to mock data. Backend verification passed 51 tests; Flutter tools did not complete during this turn, and PostgreSQL/Edge integration remain unverified. See `backend/API_CONTRACT.md` and `docs/FLUTTER_BACKEND_INTEGRATION.md` for this slice's contracts and UI behavior.
